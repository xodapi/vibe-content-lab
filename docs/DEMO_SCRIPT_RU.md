# Сценарий демонстрации Vibe Content Lab, 7 минут

Цель демонстрации: показать не «чат с LLM», а полный жизненный цикл внутреннего
AI-инструмента с контролем данных, качества и действий.

## 0:00–0:40. Контекст

> Это независимый технический Lab на публичной документации. Я выбрал её потому, что
> она позволяет показать RAG, интеграцию API и безопасность без загрузки чужих
> корпоративных данных. Цель не в том, чтобы сделать ещё один чат, а в том, чтобы
> собрать повторяемый внутренний инструмент.

Покажите README и схему компонентов.

## 0:40–2:00. RAG и источники

1. Откройте Dify workflow или Lab UI.
2. Задайте: «Как безопасно повторить генерацию после сетевой ошибки?»
3. Покажите ответ и источник.

> Модель не должна отвечать «из памяти». Она ищет фрагменты документации, и
> пользователю виден источник. Если evidence нет, корректный результат — abstention,
> а не уверенная галлюцинация.

## 2:00–3:00. Evaluation

Покажите `rag/evaluation/ground_truth.json` и `results.md` после реального запуска.

> Я разделяю retrieval и генерацию: Hit@K/MRR показывают, нашёл ли поиск нужный
> фрагмент. Дальше отдельно оцениваются цитаты и полезность ответа. Набор начинается
> с восьми вопросов, затем пополняется реальными ошибками и вопросами сотрудников.

Не называйте метрики до реального запуска.

## 3:00–4:20. Контролируемая генерация

1. Введите тестовый prompt и модель.
2. Нажмите «Получить бесплатную смету».
3. Покажите, что кнопка запуска появляется только после оценки.

> Генерация денег стоит. Поэтому последовательность фиксирована: `estimate` →
> проверка параметров и стоимости человеком → отдельное подтверждение → `generate`.
> Ключ не приходит в браузер, а повторные запросы используют idempotency key.

Не подтверждайте реальный платный запрос на демо без согласованного лимита.

## 4:20–5:20. Эксплуатация

Покажите:

- `scripts/harness.ps1 check`;
- успешный локальный `test`;
- GitHub Actions после публикации репозитория;
- Docker Compose и runbook.

> У прототипа есть тесты, сборка и документация развёртывания. Это не доказывает
> production SLA, но показывает путь, по которому MVP становится регулярным
> внутренним сервисом.

## 5:20–6:20. Low-code и интеграция

Покажите Dify canvas и n8n workflow, только после реальных запусков.

> Один и тот же контур сделан двумя способами: pro-code сервис для контролируемой
> интеграции и low-code workflow для регулярного бизнес-сценария. Это позволяет
> выбирать инструмент под риск и владельца процесса, а не по моде.

## 6:20–7:00. Честное завершение

> Что ещё не заявляю: uptime, качество на корпоративных документах и экономический
> эффект. Их можно подтвердить только пилотом: согласовать baseline, добавить
> representative eval set, включить логирование и измерить результат через 2–4 недели.

## Вопросы, на которые нужно быть готовым ответить

| Вопрос | Короткий ответ |
|---|---|
| Почему Chroma? | Локальная векторная БД, прозрачный MVP без внешнего vendor lock-in. |
| Почему не просто Dify? | Dify ускоряет workflow, а FastAPI нужен для контрактов, webhooks, audit trail и контролируемых действий. |
| Как не утекут документы? | Для demo только публичный источник. В корпоративном пилоте: классификация данных, отдельный контур, least privilege, retention policy. |
| Как измеряете качество? | Сначала retrieval метрики и ручной review цитат, затем task completion на representative наборе. |
| Что делаете при ошибке модели? | Показываем источник, разрешаем abstention, логируем, добавляем случай в regression suite. |
